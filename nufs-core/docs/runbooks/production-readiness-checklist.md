# NUFS 上线验收清单（Production-Readiness Checklist）

本清单把"能否上线"拆成**可逐项勾选、带证据/命令**的门禁表。每一项标注
**[强相关｜中相关｜按规模决定]** 与当前状态 **[✅ 已验证｜⚠️ 部分/代码存在｜✗ 缺失｜⏳ 待上线复验]**。
它是 5-9 可用性分级验收的可执行翻译，不是纸面陈述。

> 验收原则：**"代码里存在" ≠ "验证过" ≠ "在目标形态验证过"**。三者的上线权重不同。
> 单机 harness 验证（✅）升级为"具备上线能力"（决定性）必须以**真实多机/helm 落地复验**（⏳）为准。

---

## 状态图例

- **✅ 已验证**：本机真实跑通过、有门禁（drill 退出码 / 单元测试）与证据
- **⚠️ 部分**：代码存在且单机验证过，但**目标形态（多机/生产部署）未验证**
- **✗ 缺失**：无实现或无处运行
- **⏳ 上线前必做**：必须补齐才能下"可上线"结论
- **📈 按规模**：是否达成取决于目标规模/规格，需先定义 SLO

## 建议的下一步

1. **用 `make verify-docker` 锁住单机基线**（本清单 D2）——macOS 宿主跑 `make verify` 会被端口耗尽假失败干扰，直接进 Linux 容器（`make verify-docker`，无需网络，复用宿主 Go 缓存）拿到干净基线——先保证"每次改动不破坏已达标项"。`make verify` 已含 指标-告警一致性门禁（E3 的静态部分）。
2. **定义上线规格**（对象数/吞吐/节点数/是否多可用区）——让 📈 项可判。
3. **做一次真实多机 + helm 复验**——这是把 ✅(单机) 升级为可上线结论的决定性步骤。
4. **补 CI**——让 `make verify` 成为每次提交的自动门禁。
